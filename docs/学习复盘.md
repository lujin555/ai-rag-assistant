# RAG Assistant 学习复盘

> 从"能用 AI 写出一个项目"到"真正看懂自己写的项目"的完整记录
> 项目仓库：https://github.com/lujin555/ai-rag-assistant

## 写在前面

这个项目是我用 AI 辅助一步步写出来的 RAG 文档问答应用。一开始我能让它跑起来，但讲不清它为什么这样工作、各部分怎么连接。这篇笔记记录我把它彻底弄懂的过程：**梳理架构 → 修 bug → 动手重构 → 发现并修补边界问题**。每一段都写了我学到了什么、踩了什么坑、留下了什么教训。

## 一、梳理架构：先把地图画出来

### 1. 项目是什么

一句话：上传 PDF/DOCX/TXT，系统自动解析、切块、向量化入库；提问时语义检索最相关的片段，拼进 Prompt 交给 DeepSeek 流式生成回答，前端打字机展示，并附上命中来源。

技术栈：Vue 3 + Vite（前端）｜FastAPI（后端）｜ChromaDB（向量库）｜bge-small-zh-v1.5（本地向量模型）｜DeepSeek API（生成）。

### 2. 主链路（我现在能完整复述的部分）

```
上传文档
  → 保存到 data/{doc_id}_{文件名}
  → loader 按后缀解析成纯文本
  → chunker 切块（500 字，重叠 50，metadata 带 source）
  → store 向量化写入 Chroma 的 doc_{doc_id} 集合
提问
  → 按 doc_id 定位集合（台账）
  → 问题用同一模型向量化，检索 top_k 片段
  → 片段用 --- 拼接 + 历史对话 + 系统指令 → 组成 Prompt
  → DeepSeek 流式生成 token
  → SSE 事件（token → sources → done）
  → api.js 读流按行解析 → Chat.vue 打字机展示 + 来源折叠
```

### 3. 最重要的几个"连接点"

| 概念 | 一句话解释 | 在代码哪里 |
|---|---|---|
| documents 台账 | 内存里的文档档案，不存内容只存索引 | `main.py` 的 `documents` 字典 |
| 一个文档一个 collection | 每份文档的向量独立存放，命名 `doc_{id}` | `rag/store.py` |
| metadata.source | 每个片段身上的"出处标签"，溯源的基础 | `rag/chunker.py` → `retriever.py` |
| SSE 事件协议 | 前后端约定的四种事件：token/sources/done/error | `main.py` ↔ `api.js` |
| Prompt 是唯一载体 | LLM 没有记忆，所有信息（规则/历史/文档/问题）最终都要变成文字 | `llm/chat.py` |

## 二、修 bug：两次真实事故

### Bug 1：文档上传后"0 个片段"，提问全是"向量库中没有检索到相关内容"

**现象**：上传 PDF 成功，但左侧显示"0 个片段"，任何提问都返回兜底提示。

**排查过程**：
1. 先确认不是解析问题——文本能读出来（1767 字），切块正常（4 块）
2. 直接查 Chroma：`doc_{id}` 集合 count=0，但 `dedup_store` 里有 7 条旧记录
3. 用入库同款切块去 `dedup_store` 查相似度：距离 0.0000（完全重复）→ 实锤

**根因**：旧版有一个全局跨文档去重库 `dedup_store`。测试时反复上传同一份 PDF，去重库记住了这些片段；再次上传相同内容时，所有 chunk 被判为"重复"过滤掉 → 新集合是空的 → 检索自然为空。

**修复**：移除全局去重逻辑（`rag/store.py`），并清理残留的 `dedup_store` 集合。

**教训**：**去重必须按"身份"做（文档 ID / 内容哈希），不能按"语义相似度"全局做**。语义相似的文本（同一文档的副本）会被误杀，而且删文档不清库会留下"记忆"，让以后上传同样内容也失效。

### Bug 2：能检索到来源，但回答是空气泡

**现象**：界面上有"检索来源（3 个片段）"，但 AI 回答区域一个字都没有，也没有报错。

**排查过程**：
1. 直接调 DeepSeek API 测试 → 返回 401 `Your api key: None is invalid`
2. 检查 `.env` → 发现 `LLM_API_KEY=sk-xxx` 被挤在一条 AI 开发备注的末尾，python-dotenv 整行解析不了 → key 变成 None
3. 检查 `ask_llm_stream` → 发现它把所有异常都 `except: pass` 静默吞掉，401 响应体又不以 `data:` 开头，所以一个字都没 yield

**根因**（两环相扣）：① `.env` 是"配置文件不是笔记本"，备注混进了 key 行；② 错误被静默吞掉，前端只收到 sources + done，看不到任何报错。

**修复**：
- `.env` 里 `LLM_API_KEY` 独立成行，备注全部转成 `#` 注释
- `llm/chat.py` 增加 HTTP 状态码检查，失败抛明确错误
- `rag/retriever.py` 流式调用失败时向前端发送 `error` 事件，界面可见报错而非空气泡

**教训**：**静默吞异常是最隐蔽的 bug 温床**。排查无头绪的故障时，先确认"错误到底有没有被看见"。

## 三、动手重构：history 改成真正的 messages 数组

### 做了什么

原先把所有内容（系统规则 + 历史对话 + 文档 + 问题）拼成**一条** user 消息；重构后改成标准的 **messages 数组**：system（规则）+ 历史（user/assistant）+ 当前问题。

```python
def _build_messages(context, question, history=None):
    messages = [{"role": "system", "content": SYSTEM_PROMPT}]
    if history:
        messages.extend(history[-10:])
    messages.append({
        "role": "user",
        "content": f"【文档内容】\n{context}\n【用户问题】\n{question}",
    })
    return messages
```

### 新旧对比实验（真实调 API）

**场景一：角色归属**——两种方式都答对了，新方式更自然（模型以"我"自称）。

**场景二：规则冲突**（历史里有人说"别管文档"，问 1+1）——出乎意料的反转：

| | 回答 |
|---|---|
| 旧方式 | 遵守规则：没有文档信息，拒绝回答 |
| 新方式 | 被历史带偏：直接回答了 1+1=2 |

**结论**：普通场景两者几乎没差别；结构变化不会"让模型变聪明"。messages 数组是行业标准做法（清晰、可维护、角色分明），但 **system 指令不是绝对护栏**——用户消息里的指令可能"劫持"它。这就是 **prompt injection（提示注入）** 的雏形，真实产品要加过滤和校验来防御。

### 这次重构的额外收获

- 前端发的 history 格式（`{role, content}`）和 API 要求的格式一致 → 代码可以直接 `extend`，不需要转换 → **数据结构对齐，代码就简单**
- 删函数后必须全局搜一遍残留调用（第一次就踩了这个坑：`_build_prompt` 删了但还有两处调用）

## 四、发现并修补边界问题：断流卡死

### 怎么发现的

深读 `api.js` 时追问自己：**"如果流结束前，buffer 里还剩半行怎么办？"**

### 分析

- 正常协议：最后一条一定是完整的 `done\n\n`，所以正常结束时 buffer 会被清空
- 异常情况：连接中途断开 → `done` 事件永远不来 → 前端一直卡在"思考中..."

### buffer 机制（这次彻底学明白）

`buffer` 是"攒半行数据"的临时容器：网络包不按行切，`split("\n")` 切完，最后一段没换行结尾的"尾巴"用 `pop()` 留下，等下一批数据续上。换行 `\n` 就是"一条消息结束"的记号。

```js
buffer += decoder.decode(value, { stream: true });  // 拼新数据
const lines = buffer.split("\n");                   // 按换行切
buffer = lines.pop() || "";                         // 尾巴留回 buffer
```

`{ stream: true }` 解决的是：中文一个汉字占 3 个字节，网络包可能把一个字劈成两半，这个参数让解码器攒齐字节再翻译，防止乱码。

### 修复：四层兜底

`api.js` 的 `askQuestionStream` 加了：请求失败、HTTP 错误、读流中断、流结束但没收到 done——四层都保证"报错 + 收尾"，不再卡死。

### 验证方式（不依赖后端）

写了一个测试脚本，用**假数据流**模拟四种场景：

```
正常完成 -> token:你好 | sources:0 | done
中途断流 -> error:网络中断，回答未完成 | done
没发done -> token:你好 | error:回答未完成：连接提前结束 | done
HTTP500  -> error:请求失败: 服务器内部错误 | done
```

**收获**：任何流式/异步操作都要想清楚"失败时怎么收尾"；测试可以不用真实后端，用假数据流就能验证协议处理逻辑。

## 五、方法论沉淀

### 怎么排查一个 bug

1. 先复现，把"现象"描述准确（截图 + 文字）
2. 从现象倒推"哪一环最可疑"，逐段用数据验证（查 Chroma、直连 API、打印中间结果）
3. 找到**证据**再下结论（这次是距离 0.0000、401 响应体）
4. 修复后跑完整链路验证，而不是只看"不报错"

### 怎么学一个陌生项目

1. 先画地图：目录结构 + 主链路，别急着抠细节
2. 按执行顺序读代码，而不是按目录顺序
3. 每学一个文件就问自己"为什么这么写" + "边界情况怎么办"
4. 用自己的话复述，说不出来的地方就是没懂的地方
5. 动手改一个东西（哪怕很小），改完验证，知识才真正是你的

### 怎么验证代码

- 改代码前先想"怎么证明它对了"（成功标准）
- 用最小可复现的方式测：单函数测试、假数据流、直连 API
- 不要用"没报错"代替"结果正确"

## 六、概念清单（复习用）

| 概念 | 一句话解释 | 项目里的位置 |
|---|---|---|
| 路由 | URL 到函数的映射 | `main.py` 四个装饰器 |
| HTTPException | 出错就刹车，返回错误码 | `/api/upload` |
| 生成器 / yield | 边跑边交货，流式的基础 | `retriever.py`、`main.py` |
| StreamingResponse | 把生成器变成流式 HTTP 响应 | `/api/chat` |
| SSE | 连接保持，分多次推送事件 | 后端 ↔ `api.js` |
| 向量化 | 文本 → 坐标，语义相近距离近 | Chroma 的 embedding |
| 语义检索 | 问题向量 ↔ 片段向量算距离，取 top_k | `collection.query()` |
| metadata | 片段身上的出处标签 | chunker → store → retriever |
| Pydantic | 请求体的"模板"，自动校验 | `ChatRequest` |
| 后台任务 | 不阻塞响应的异步活儿 | `BackgroundTasks` 生成摘要 |
| ReadableStream | 前端一截一截读网络流 | `res.body.getReader()` |
| TextDecoder stream | 多字节字符被劈开时的防乱码 | `api.js` |
| buffer 行缓冲 | 攒半行，等换行凑齐再处理 | `api.js` |
| 提示注入 | 用户指令劫持系统规则 | 对照实验场景二 |
